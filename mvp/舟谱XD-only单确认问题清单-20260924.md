## 一、为什么问（背景，一段话）

我们按"**以 XD 履约单状态=已完成来结算促销费用，不管它有没有对应的 SXD 销售订单**"这个新口径改造了核算。改造后发现：**有 2644 张订单只有 XD 履约单、在我们拿到的数据里查不到对应的 SXD 销售订单**（下文简称 **XD-only 单**）。

- **SXD** = 前端销售订单号，代表"用户下了单"，只有它能抽出完整订单明细。
- **XD** = 后端履约单号，代表"仓库发货/完成"。
- **XD-only 单** = 只有 XD、找不到 SXD 的单。

这批单目前已被我们**建成正式订单并纳入核算**，直接影响"满赠发了多少赠品、费用结算多少"。但它们的**业务来源和是否独立计费还没跟你们确认过**，是我们目前唯一悬着的计费风险点。**在你们回复前，这部分结算结果我们标为"待确认"，不作为最终对账依据。**

---

## 二、核心疑问（一句话）

> 这 2644 张 XD-only 单，**到底是 2644 笔独立的真实交易，还是某些已有 SXD 订单的拆分/二次履约/补发？** 如果是后者，我们就会重复计费。

## 六、舟谱回复与结论（2026-09-24）

舟谱侧对七个问题逐条书面回复如下（原话摘录）：

| # | 问题 | 舟谱回复 |
|---|---|---|
| Q1 | XD-only 怎么产生的 | **业务员自行下单**——很多客户不想自己下单，由业务员代下单 |
| Q2 | 独立交易还是拆分/补发 | **独立交易** |
| Q3 | 综合订单号为何全空 | **本来就没有上游 SXD** |
| Q4 | 单号不相交是否符合预期 | **符合预期**：用户平台下单生成 SXD，业务员代下单直接生成 XD |
| Q5 | 0 金额的已完成单是什么 | **兑换商品**，进不进促销费用核算都不影响 |
| Q6 | 满赠相关单是否有对应 SXD | 如果用户下单，则有对应的 SXD（即业务员代下单的 XD-only 满赠单本就无 SXD，是独立真实履约） |
| Q7 | "已完成"可否作为结算节点 | **确认订单状态='已完成'作为费用结算节点** |

### 结论

1. **重复计费风险（#12）关闭**：XD-only 单是业务员代客下单产生的**独立交易**，不是任何 SXD 订单的拆分/二次履约/补发 → 不会与现有 SXD 单重复计费。这与我们核到的"XD-only 单号(2644) 与 SXD 关联下游 XD 单号(4050) 交集=0"互相印证。
2. **综合订单号全空属正常**：本就没有上游 SXD，不是字段漏导，**无需补导数据**。
3. **单号来源二分法明确了**：用户平台下单 → SXD；业务员代下单 → 直接 XD。两套单号天然不相交，我们的关联口径没有漏字段。
4. **0 元兑换商品单**：对促销费用核算无影响（金额=0 不会触发满赠"雪碧≥100"合格判定，也不带返券）→ 保留现状，无需特殊排除。
5. **满赠 18 个 XD-only 抱枕保留计入**：是业务员代下单的真实满赠履约 → **实赠抱枕 100 个口径成立**（用户此前"一共才 100 个抱枕"的直觉得到供应商侧确认）。
6. **结算节点确认**："已完成"作为费用结算节点，与我们"已完成+T-2"口径一致。

### 对结算的影响

**无重算，数字全部不变**：XD-only 2644 单 / 满赠实赠抱枕 100 / 合格 142 / release 候选 179 / 返券 45×15=675 元。已在 MVP 库落一条确认台账（`result_quality_issue` issue_id=65，level=提示，calc_batch=11）作为审计证据；兴路强侧隔离 Δ=0，外键无违例。
