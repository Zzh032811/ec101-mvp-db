# EC101 数据库与 Template 字段差异及改造方案

## 1. 文档目的

本方案以客户提供的 `Template_系统主要功能模块要求 -For客户.xlsx` 为业务展示和导入字段契约，说明当前 SQLite MVP 数据库与模板的差异、建议的模型调整、迁移影响和查询视图。

本次约定：模板中的“销售明细（订货明细）”对应数据库的订单明细，而不是模板中另一张“订单明细”工作表。后者含发货、退货和券分摊等扩展字段，可作为订单履约和券核销的补充来源。

目标是让模板字段可稳定查询、可追溯且可用于费用核算；不是把模板的每一列都重复存进数据库。

## 2. 现状与改造原则

当前模型已有 RAW、STANDARD、CORE、RESULT 四层，以及客户、商品、订单、活动、券台账、履约和费用结果等基础实体。它的侧重点是“促销费用闭环”，而模板还要求“平台运营主数据、订单履约和商品库存”的完整表达。

改造遵循以下原则：

1. 保留现有 RAW、TPM、规则、核算和结算表；它们是费用闭环所必需的，不因模板未展示而删除。
2. 外部单号、客户号、商品号、条码、活动 ID 和券号一律以 `TEXT` 保存。模板中出现科学计数法的样例，不能作为数值型建模依据。
3. 主数据名称、活动统计和订单展示字段优先通过关联或视图输出。只有历史快照、来源原值或无法可靠推导的事实才物理落列。
4. 不以名称关联活动、业务员或优惠券。所有跨表关系使用内部主键；平台侧稳定编号另设业务键。
5. 历史数据只做有证据的回填。无法确认的外键和新增事实字段保留 `NULL`，并在质量问题表中记录，不允许按名称猜测。

## 3. 差异总览

| 模块 | 模板要求 | 当前模型 | 差异结论 |
|---|---|---|---|
| 业务员 | 编号、名称、账号、等级、电话、状态、备注 | 仅在客户和券台账中保存业务员名称文本 | 缺业务员主数据及外键关系 |
| 客户 | 编号、名称、类型、区域、详细地址、电话、添加时间、所属业务员 | 已有编号、名称、类型、区域、创建时间；业务员为名称文本 | 缺地址、电话及业务员外键 |
| 销售明细 | 订单、客户、商品、数量金额、活动编号、券号、实付金额、业务员、来源和状态 | `order_header` + `order_line` 覆盖主干 | 缺行级活动/券关系、实付金额和业务员外键 |
| 订单履约补充 | 供货商、重量、已发/未发/退货、券优惠金额 | 仅有订单级履约和订单行退货数量 | 缺订单行履约数量、重量、券分摊和供货商快照 |
| 活动 | 平台活动 ID、活动类型/券类型、对象、方式、发放类型、总数/已发/已用、状态 | 内部活动 ID、规则、范围、券发放/使用规则 | 缺明确的平台活动编号；套餐促销不具备结构化规则；缺统一统计输出 |
| 优惠券 | 活动、券号、客户、领取/使用时间、使用期、订单、优惠金额 | `coupon_ledger` 基本覆盖 | 使用订单只是文本，缺强外键和订单行分摊 |
| 库存 | 成本金额、实际/占用/可用/实际可用/总库存 | 商品表中仅保存部分当前库存字段 | 缺成本金额、实际可用、库存总数和快照时间 |
| 商品 | 口味、包装、容量、单位条码、整箱条码、每箱数量、产品代码、备注 | 单一条码、规格、箱规/换算、映射产品码 | 缺可一一对应的商品属性和双条码模型 |

## 4. 建议的数据模型调整

### 4.1 新增业务员主数据

新增 `salesperson`，粒度为“经销商平台内一名业务员一条”。

| 字段 | 说明 |
|---|---|
| `salesperson_id` | 内部主键 |
| `dealer_platform_id` | 所属经销商平台外键 |
| `platform_salesperson_no` | 模板“业务员编号”，业务键 |
| `salesperson_name` | 模板“业务员名称” |
| `account`、`grade`、`phone`、`status`、`remark` | 与模板一一对应；电话为 `TEXT` |

新增唯一约束：`UNIQUE(dealer_platform_id, platform_salesperson_no)`。在 `customer` 和 `order_header` 增加可空 `salesperson_id` 外键；保留旧 `salesperson_name` 至迁移完成后再决定是否废弃，避免历史数据丢失。

### 4.2 补齐客户字段

在 `customer` 增加：

```text
detail_address TEXT
phone          TEXT
salesperson_id INTEGER REFERENCES salesperson(salesperson_id)
```

客户名称、类型、区域、添加时间继续使用已有字段。`所属业务员`通过 `salesperson_id` 关联输出，不再以名称作为正式关系键。

### 4.3 重构订单明细的事实边界

`order_header` 保留订单级字段：单据编号、下单时间、客户、业务员、订单来源、订单类型、订单状态、支付方式和支付状态。

`order_line` 作为模板“销售明细”中每个商品行的事实表，建议新增：

```text
line_no                 INTEGER        -- 源明细行号；同一商品可多次出现
paid_amount             NUMERIC        -- 模板“实付金额”，源值
weight_kg               NUMERIC        -- 模板“重量(kg)”，有来源时写入
shipped_qty             NUMERIC        -- 已发货数量
unshipped_qty           NUMERIC        -- 未发货数量
```

现有 `order_qty`、`order_unit`、`base_qty`、`base_unit`、`pre_discount_amount`、`discount_amount`、`unit_price` 和 `return_qty` 可继续对应数量、金额和退货字段。应把唯一约束从 `UNIQUE(order_id, product_id)` 调整为 `UNIQUE(order_id, line_no)`；否则同一订单内同一商品因不同活动或拆单产生多行时无法保存。

供货商名称不建议重复写入每个订单行。展示时从 `dealer_platform.dealer_name` 输出；只有来源要求“交易时供货商原值”时，才在订单头增加 `supplier_name_snapshot`。

### 4.4 新增订单行活动与订单行券关联

当前 `order_activity` 的粒度为“订单 × 活动”，不足以对应销售明细中某商品行命中某活动的事实。保留该表作为订单级汇总/核算入口，同时新增两张明细关联表：

```text
order_line_activity
  - order_line_activity_id
  - order_line_id                 FK → order_line
  - activity_id                   FK → activity
  - rule_id                       FK → activity_rule，可空
  - eligible_amount
  - actual_benefit_amount
  - evidence_ref
  - UNIQUE(order_line_id, activity_id, rule_id)

order_line_coupon
  - order_line_coupon_id
  - order_line_id                 FK → order_line
  - coupon_id                     FK → coupon_ledger
  - allocated_discount_amount
  - evidence_ref
  - UNIQUE(order_line_id, coupon_id)
```

`order_activity` 的订单级优惠金额应由行级活动聚合或由平台订单活动明细直接导入，并保留来源证据。`coupon_ledger.use_order_no` 应改为/补充 `use_order_id` 外键；订单号文本继续保留为源值与审计证据。只有订单号经文本校验成功后才回填该外键。

### 4.5 明确活动平台标识并支持组合促销

在 `activity` 增加 `platform_activity_no TEXT`，并建立 `UNIQUE(dealer_platform_id, platform_activity_no)` 的非空唯一约束。内部 `activity_id` 仍是主键；`activity_import_key` 仍用于导入幂等，三者不互相替代。

当前模型已经能表达满减、满赠和送券。为结构化支持模板列出的“套餐（组合促销）”，建议扩展：

```text
activity_rule
  - benefit_calc_type   TEXT  -- fixed_amount / percentage_discount / gift / coupon
  - discount_rate       NUMERIC

activity_bundle_item
  - bundle_item_id
  - rule_id             FK → activity_rule
  - product_id          FK → product，可空
  - product_scope_value TEXT，可空
  - required_qty        NUMERIC
  - required_unit       TEXT
```

一个套餐规则可关联多条必买商品行，并可表达“500 可乐 + 雪碧打九折”。活动的总数、已发放数量、已使用数量不存冗余列，统一由券台账聚合。

### 4.6 将库存从商品主表拆为快照事实

保留 `product` 的主数据字段，但将库存改为 `inventory_snapshot`，粒度为“平台商品 × 快照时间 × 导入批次”。

```text
inventory_snapshot
  - inventory_snapshot_id
  - dealer_platform_id             FK → dealer_platform
  - product_id                     FK → product
  - snapshot_at                    TEXT
  - batch_id                       FK → raw_import_batch
  - actual_stock
  - occupied_stock
  - available_stock
  - actual_available_stock
  - total_stock
  - cost_avg_price
  - cost_amount
  - shelf_status
  - UNIQUE(dealer_platform_id, product_id, snapshot_at, batch_id)
```

改造后 `product` 不再承载会随时变化的库存和成本数值。最近一条快照通过视图提供给运营端，历史快照可用于追溯活动期间的赠品可用性。

### 4.7 补齐商品属性和条码语义

在 `product` 增加或明确以下字段：

```text
manufacturer_product_code TEXT  -- 模板“产品代码”，不等同于太古映射码
flavor                    TEXT
package_type              TEXT
capacity                  TEXT
unit_barcode              TEXT
case_barcode              TEXT
units_per_case            NUMERIC
remark                    TEXT
```

`platform_product_no` 对应销售/库存来源中的商品编号；`manufacturer_product_code` 对应商品资料中的产品代码；`swire_product_code` 仅保留为跨系统映射结果。旧 `barcode`、`spec`、`box_conversion` 可先保留用于兼容，迁移完成后由明确字段取代。

## 5. 模板字段的一一对应查询视图

为避免前端和导出逻辑跨多表拼接，新增只读视图。视图是模板契约，不改变 CORE 事实表的职责。

| 视图 | 模板工作表 | 输出口径 |
|---|---|---|
| `vw_template_sales_detail` | 销售明细（订货明细） | 订单行，关联订单、客户、商品、业务员、行级活动和券；多券情形按券分摊行展开或由导出参数选择汇总 |
| `vw_template_order_detail` | 订单明细 | 在销售明细基础上增加供货商、重量、发货/未发货/退货及券优惠金额 |
| `vw_template_salesperson` | 业务员列表 | 业务员主数据 |
| `vw_template_customer` | 客户资料 | 客户及所属业务员 |
| `vw_template_activity_summary` | 促销功能模块 | 活动平台编号、名称、类型、对象、方式、发放类型、券统计和状态 |
| `vw_template_coupon_detail` | 优惠劵发放明细 | 券台账、活动、客户、业务员、订单及核销金额 |
| `vw_template_activity_detail` | 活动明细表 | 券、满减、满赠等活动执行事实的统一 `UNION ALL` 视图 |
| `vw_template_inventory_current` | 库存 | 每商品最近一次库存快照 |
| `vw_template_product` | 商品、商品1 | 商品属性、产品代码、双条码和包装信息 |

其中 `vw_template_sales_detail` 的字段映射如下：

| 模板字段 | 来源 |
|---|---|
| 单据编号、下单时间、订单来源、订单类型、订单状态 | `order_header` |
| 客户编号、客户名称 | `customer` |
| 商品编号、商品名称、商品目录、规格、商品条码、单位 | `product` + `order_line` |
| 数量、优惠前金额、优惠金额、实付金额 | `order_line` |
| 活动编号 | `activity.platform_activity_no`，经 `order_line_activity` 关联 |
| 优惠券编号 | `coupon_ledger.coupon_no`，经 `order_line_coupon` 关联 |
| 业务员 | `salesperson.platform_salesperson_no` 或名称；导出显示规则另定 |

## 6. 数据迁移与接口影响

审计时现有库包含 4,784 条客户、11,784 条商品、9,622 张订单、135,686 条订单行、421 条订单活动、103 条券台账和 9,043 条履约记录。因此迁移必须以“扩展、校验、切换”方式进行，不能重建后直接覆盖现有数据库。

### 6.1 历史数据迁移

1. SQLite 迁移前创建带时间戳的数据库备份，并在单一事务中执行结构变更。
2. 新增列以可空方式上线；先保留旧的业务员名称、条码、规格和库存字段，完成核验后再删除或停止写入。
3. 业务员、平台活动编号、地址/电话、订单行履约数据和商品属性从有权威来源的模板或平台导出导入；没有来源不造数。
4. 历史订单行没有可靠 `line_no` 时，按原始文件行号生成，并记录 `batch_id` 和来源行号。
5. 只有券号与订单号均以文本保存且通过经销商平台、客户、时间等证据核验时，才写入 `use_order_id`、`order_line_coupon`。
6. 现有库存字段先迁移为一条“迁移快照”，快照时间使用导入批次时间；不能证明时点时标记为迁移基线，不宣称为业务实时库存。

### 6.2 API、前端和核算影响

| 范围 | 影响 | 处理方式 |
|---|---|---|
| SQLite DDL | `customer`、`order_header`、`order_line`、`activity`、`product` 需变更；新增 5 张事实/维度表 | 编写独立迁移脚本，保留兼容列 |
| 现有 API | `api/server.py` 当前直接查询旧表 | 先保持已有接口字段；新增模板视图接口或将读接口逐步切换到视图 |
| 前端业务数据页 | 现有订单行接口不含实付、活动/券行级信息 | 增加新字段和筛选项，避免以订单级活动误展示为商品行活动 |
| 费用核算 | `order_activity`、`result_entitlement` 目前按订单活动核算 | 行级活动导入完成后，定义订单级聚合规则并以抽样订单复核金额；不得直接覆盖历史结果 |
| 数据质量 | 长编号、历史活动和券关联存在精度/证据限制 | 入库时强制字符串校验；无法关联记录写入 `result_quality_issue` |

## 7. 分阶段实施建议

### 第一阶段：先建立模板查询契约

新增业务员、客户补充字段、订单行扩展、活动平台编号、商品属性和库存快照表；创建九个模板视图。此阶段不改变既有费用核算结果，目标是实现模板字段可查询、可空缺提示、可追溯。

### 第二阶段：补足行级促销事实

导入订单行活动和订单行券关联，建立订单级汇总规则，抽样复核活动优惠金额、券金额和实付金额。完成后再使费用核算优先使用行级事实。

### 第三阶段：组合促销与接口切换

导入套餐/组合促销规则及商品组合，增加相应重算规则；前端和 API 改为模板视图或新的读模型。旧接口保留一个发布周期，确认没有调用方后下线。

## 8. 验收标准

1. 模板各业务字段都有明确的“物理列、关联列、计算列或不可提供原因”，不存在隐含映射。
2. 模板“销售明细”可按订单行导出，并正确展示活动 ID、券号、实付金额、业务员、来源和状态。
3. 同一订单重复商品行可以保存；一行可关联多个活动或券，且金额分摊可追溯到源证据。
4. 业务员、客户、商品、活动和券的关联都可用外键校验，名称不再作为正式关联键。
5. 库存可按快照时间还原，商品资料可同时表达单位条码、整箱条码、包装、容量和每箱数量。
6. 迁移后执行 `PRAGMA foreign_key_check`，并对现有订单、订单行、活动、券和费用结果数量及关键金额做迁移前后对账。

## 9. 尚待业务确认的决策

1. 模板“实付金额”是订单行实收、应收，还是折后应付金额；确认后决定是否可由金额计算得出。
2. “已发货数量/未发货数量”是累计状态还是多次发运事件；若有多次发货，需要另建 `shipment` 和 `shipment_line`，不能只扩展订单行汇总列。
3. 模板“产品代码”的权威来源和命名规则，避免与平台商品编号、太古产品代码混用。
4. 同一订单行命中多张券时，平台是否提供金额分摊；若不提供，应明确汇总展示规则，不能伪造行级分摊。
5. 活动 ID 是否能从所有平台以稳定文本形式导出；若不能，必须定义平台活动业务键的生成与版本规则。
