# EC101 费用核销产品 PRD V1

## 1 文档目的

本 PRD 定义 EC101 从已验证的数据底座走向业务产品的第一阶段：建立面向业务、财务和数据团队的费用核销运营台。它不替代《EC101 数据底座建设方案 V1》或《EC101 逻辑数据模型设计说明 V1》，而是把两份设计中已经确认的对象、规则和核算结果转化为可查询、可处理、可追溯的业务界面与操作流程。

本期目标不是建设完整 DMS，也不是在页面中重新实现费用计算；目标是让任意一笔待结算费用能够从页面追溯到活动、规则、订单、履约、原始批次和核算结论，并将异常与业务确认纳入闭环。

## 2 上游依据与承接关系

| 上游交付物 | 已确认内容 | 本 PRD 的承接方式 |
|---|---|---|
| EC101 数据底座建设方案 V1 | 四层数据架构、费用订单级追溯、T-2 发放、验证 Skill 与数据底座分工 | 页面只读取和呈现已入库的 RAW、STANDARD、CORE、RESULT 结果；不绕过质量门禁生成结算结论 |
| EC101 逻辑数据模型设计说明 V1 | 经销商、客户、商品、订单、活动、履约、TPM 申请、权益、费用、质量问题和规则版本 | 以 `order_activity` 为证据链中心，以 `result_entitlement`、`result_release_candidate`、`result_fee`、`result_quality_issue` 为主要业务视图 |
| 活动费用闭环验证器 | 活动任务卡、输入质检、规则重算、支持结论、P0/P1/P2 问题、逐单证据 | 作为核算与准入引擎；运营台展示其结论、证据和待办，不复制计算公式 |
| 双平台 MVP 数据库 | 快马 兴路强与舟谱 羿柏的共库事实、权益结果、释放候选和质量台账 | 作为首版演示与接口契约的真实数据来源；上线前迁至生产数据库和服务接口 |

### 2.1 一致性原则

1. **一个核算真相来源。** 满减、满赠、返券、T-2、异常等级和结论只由规则目录与核算引擎产生；页面不得另写公式或修改核算金额。
2. **金额和实物分开。** 满减、返券等金额费用与满赠等实物权益分别呈现。赠品数量不自动换算金额；未确认单位成本时只能统计数量。
3. **未验证不等于零。** 数据窗口不足、活动配置缺失、P0 问题或券号无法归因时，必须显示“未验证”或“待确认”，不得展示为零费用或可结算。
4. **每次结果可复现。** 页面显示规则版本、计算批次、数据来源批次和计算日期；历史批次不可被新规则覆盖。

## 3 MVP 实施方案核对

《EC101 数据底座建设方案 V1》规定的演进顺序是：逻辑模型 → 活动费用闭环 MVP 实施方案 → 费用核销产品 PRD。

经核对，项目已完成了 MVP 实施的主要实物交付：SQLite MVP 数据库、DDL、导入与核算脚本、快马 兴路强和舟谱 羿柏双平台共库接入、计算批次、订单级验证样本、质量问题台账及核验输出均已存在。兴路强满减和满赠、羿柏返券和满赠已形成实际核算结果。

但仓库中未找到独立命名的《EC101 活动费用闭环 MVP 实施方案》文档。因此，本项目的情况是“实施没有跳过，实施方案文档缺失”。本 PRD 不应掩盖这一缺口，产品开发前需将以下 MVP 基线纳入实施计划并作为验收前置条件：

| MVP 基线 | 当前状态 | 产品化要求 |
|---|---|---|
| 平台准入与任务卡 | 验证器已定义，需持续执行 | 新数据批次未通过质量门禁不得进入可结算工作区 |
| 规则与计算批次 | 已有规则目录和 RESULT 批次 | API 必须按批次返回，不允许页面改写历史结果 |
| 双平台核算样本 | 已有快马 兴路强、舟谱 羿柏 | 首版界面必须能展示两类平台和金额/赠品两类权益 |
| 异常与待确认 | 已存在质量问题及开放业务项 | 异常必须支持负责人、状态、处理说明和证据链接 |
| 生产化运行 | SQLite 本地验证完成 | 产品真实使用前需迁移 MySQL、提供只读查询服务与审计日志 |

## 4 用户与使用场景

| 角色 | 核心任务 | 首版价值 |
|---|---|---|
| 业务与市场 | 判断活动是否达到兑付条件，定位异常订单并补充业务说明 | 不再依赖多个 Excel 文件人工拼接 |
| 财务与费用专员 | 查看可结算范围、对账差异、结算批次和费用归属 | 可区分可结算、待确认和不可结算金额/数量 |
| 数据团队 | 检查接入批次、字段映射、数据覆盖和质量问题 | 可将数据问题与业务结论直接关联 |
| 经销商协同人员 | 核对经销商垫付、待确认事项和对账结果 | 后续可扩展经销商门户，本期不开放外部写入 |
| 项目管理者 | 观察平台准入、核算闭环、异常积压及产品演进 | 一张运营总览掌握项目健康度 |

## 5 产品范围

### 5.1 本期开发范围

1. **运营总览**：展示平台接入状态、活动数量、金额费用、实物赠品数量、待处理异常、待结算批次及数据新鲜度。
2. **数据接入与质量**：按经销商和平台查看导入批次、文件、覆盖期间、字段映射、质量门禁及阻断原因。
3. **业务数据**：让业务人员直接查询标准化后的订单、订单明细、活动、活动明细、客户、商品、履约和订单活动关系，支持筛选、明细下钻与导出。
4. **活动中心**：查询活动配置、TPM 申请、活动范围、规则版本、预算与执行状态。
5. **权益核算台**：按活动、经销商、批次查询理论权益、实际权益、一致性、T-2 释放状态；支持金额权益和赠品权益分组。
6. **证据与异常中心**：以订单活动关系为入口，查看订单、活动规则、履约、原始批次和问题台账；对异常填写负责人、处理状态、业务说明和确认记录。
7. **核销与对账**：从已释放且无 P0 阻断的结果生成只读候选清单、经销商对账单预览和结算批次草稿；本期不发起支付。
8. **KPI 考核与分销管理入口**：在产品导航及架构中预留模块、数据契约和规划页，不建设计算、审批或写入能力。

### 5.2 本期不做

- 经销商在线订货、库存作业、物流执行、支付、发票、资金账户和真实付款。
- 全量审批流、外部经销商账号、复杂权限体系和移动端。
- 页面内自定义促销公式或直接修改已发布活动规则。
- KPI 计算、考核排名、目标分解、深度分销库存计算和渠道激励。
- 未通过准入的第三方平台正式结算。

KPI 与分销不是装饰性菜单。二者将复用经销商、客户、商品、订单、活动、履约、规则和数据质量对象；后续新增的目标、业代、线路、库存、sell-in、sell-out 等实体在应用层扩展，不改变当前 CORE 事实模型。

## 7 核心业务流程

### 7.1 数据到费用的主链路

```text
平台数据批次
→ 质量门禁
→ 标准映射与事实入库
→ 规则版本和计算批次
→ 理论权益与实际权益比对
→ T-2 释放候选
→ 异常处理与业务确认
→ 核销候选与经销商对账
→ 结算批次草稿
```

任何环节出现 P0 阻断、数据覆盖不足或费用归属不清时，链路在“待确认”停止，不能进入结算批次。

### 7.2 核销候选规则

一条结果进入核销候选需同时满足：

- 对应数据批次质量结论不是阻断；
- 有明确活动、规则版本、订单活动关系和计算批次；
- `result_release_candidate.is_candidate = true`；
- 金额费用的理论与实际权益一致，或差异已被业务确认；
- 实物权益仅按数量统计，除非赠品成本与费用承担方已确认；
- 不存在未关闭的 P0 问题。

支付方式与支付状态只展示风险，不作为 T-2 候选的排除条件。该口径与数据底座建设方案和当前核算规则一致。

## 8 页面与关键交互需求

### 8.1 运营总览

- 默认显示当前有效计算批次；可切换历史批次但不可编辑。
- 以经销商、平台、活动类型、活动期间筛选。
- 金额卡与实物卡分开展示；金额明确币种和是否可结算，实物展示应赠/实赠/差异数量。
- 显示“数据新鲜度、质量门禁、P0 未关闭数、待业务确认数、待结算数”。

### 8.2 业务数据

- 业务数据按业务对象提供查询入口，不直接把数据库表名作为页面名称。
- 首版对象包括订单、订单明细、活动、活动明细、客户、商品、履约记录和订单活动关系。
- 所有列表支持经销商、平台、业务时间、批次和关键编号筛选；订单、活动和订单活动关系支持关联下钻。
- 详情页同时显示标准化字段、平台原始字段、来源批次、来源文件和源行号，形成“业务字段可读、数据血缘可追溯”的双层视图。
- 提供当前筛选结果导出，首版使用带 UTF-8 BOM 的 CSV，确保 Excel 打开时中文不乱码；导出文件必须带对象名称、筛选条件和生成时间。
- 业务数据模块只读，不允许直接修改 CORE 事实；修正必须回到数据映射、接入批次或核算确认流程。

### 8.2 活动中心

- 活动列表展示活动名称、平台、经销商、期间、促销方式、TPM 申请、预算、规则版本与执行状态。
- 活动详情展示活动范围、阶梯、权益、订单命中数、理论/实际结果、异常摘要和证据入口。
- 仅允许具备业务确认权限的用户发起“规则确认记录”；规则变更生成新版本，不能覆盖历史计算。

### 8.3 权益核算台

- 列表粒度为订单×活动×计算批次。
- 金额权益列：参与商品金额、理论优惠、平台实际优惠、差异、T-2 状态。
- 赠品权益列：应赠数量、实赠数量、差异、费用单价状态；不把数量误显示为人民币。
- 点击单行进入证据链抽屉，包含原始批次、订单、履约、规则、活动配置和异常。

### 8.4 证据与异常中心

- 异常必须显示级别、对象、原因、证据引用、计算批次、责任方、处理状态和最后更新时间。
- 支持“待确认、处理中、已确认、关闭”四个处理状态；关闭必须留存确认人、时间和处理说明。
- P0 问题在所有列表与结算批次中强提醒，并阻止进入候选结算。

### 8.5 核销与对账

- 按经销商、结算期间和费用类型汇总可结算候选。
- 对账单至少包含活动、订单范围、权益/费用、异常扣除或待确认原因、规则版本和数据批次。
- 结算批次为“草稿、待业务确认、待财务确认、已确认、已上账”状态；首版只实现草稿与确认记录，不连接支付或 ERP 凭证。

### 8.6 KPI 与分销规划页

- KPI 规划展示将复用的指标：销量、活跃客户、活动执行率、权益差异率、异常关闭时效、回款/支付风险。
- 分销规划展示将复用的对象：经销商、区域、商品、订单、库存、sell-in、sell-out、终端覆盖。
- 显示“依赖数据尚未齐备”的字段，包括独立业代/线路主数据、目标任务、深度库存和完整 sell-in 数据。

## 9 数据与接口约束

| 产品能力 | 最小读取对象 | 关键约束 |
|---|---|---|
| 接入与质量 | raw_import_batch、raw_file、std_field_mapping、std_quality_check | 禁止将未通过质量门禁的数据标记为可结算 |
| 活动与预算 | tpm_application、activity、activity_rule、activity_rule_benefit、activity_scope、rule_catalog | TPM 预算审批与订单执行分离；不能以订单页面编辑预算 |
| 核算与证据 | order_header、order_line、order_activity、fulfillment、result_entitlement、result_calc_batch | 订单号与券号均按字符串传输和展示 |
| 费用与结算 | result_release_candidate、result_fee、result_quality_issue | 同时显示计算批次与规则版本；无 P0 才可生成候选 |
| 规划模块 | 上述 CORE 与 RESULT 对象 | KPI/分销只读规划，不产生计算或写入 |

产品接口第一阶段采用只读查询服务。SQLite 仅作为 MVP 核算验证库；业务使用前迁移至 MySQL，并通过服务层提供分页、筛选、权限和审计能力。

## 10 非功能与审计要求

- 任何金额、数量、状态和结论均可定位到计算批次、规则版本、导入批次和来源平台。
- 订单号、券号、使用单号必须使用字符串，禁止前端数值转换。
- 页面所有金额以定点两位小数显示；比较容差遵循核算引擎的 0.01 元规则。
- 结算候选、异常状态变更和业务确认必须有操作人、操作时间与说明。
- 数据不足时以“未验证/待确认”展示，不能使用默认零值代替。

## 11 验收标准

1. 可从任意兴路强或羿柏活动结果追到活动、规则、订单、履约、计算批次和原始导入批次。
2. 业务数据可以查询至少八类标准化对象，并支持筛选、详情下钻和 CSV 导出。
3. 运营总览、核算台和对账候选的金额与实物数量分别与 RESULT 层核算结果一致。
4. P0 问题、数据阻断和未验证数据不能进入可结算候选。
5. T-2 候选展示与 `result_release_candidate` 一致，支付状态不改变候选资格。
6. 满赠的数量与金额不混淆；未确认单价的赠品不产生金额结算。
7. KPI 与分销入口可展示其依赖的数据对象及缺口，但不产生虚构指标或业务写入。

## 12 分阶段交付与决策点

| 阶段 | 交付 | 前置条件 |
|---|---|---|
| A MVP 实施方案补齐 | 将现有数据库、接入、计算任务、样本、验收与上线边界正式成册 | 与当前双平台库和验证输出核对一致 |
| B 产品只读版 | 运营总览、活动中心、核算台、证据异常、对账预览、KPI/分销规划入口 | 建立只读数据服务或稳定快照接口 |
| C 协同闭环版 | 异常分派、确认记录、结算批次状态与审计 | 明确角色与确认责任人 |
| D 生产对接版 | MySQL、任务调度、权限、ERP/SAP 上账接口 | 业务确认费用承担、支付与财务边界 |
| E 增长运营版 | KPI 考核与分销管理 | 补齐业代、线路、目标、库存、sell-in/sell-out 数据 |

## 13 当前风险与待决事项

| 风险或待决事项 | 对产品的影响 | 处理原则 |
|---|---|---|
| 羿柏满赠差异及返券双单号归因 | 部分结果不能进入最终费用结论 | 在异常中心保留逐单证据，待业务确认后生成新计算批次 |
| 快马券类活动配置未完整结构化 | 券台账可查但不能完整核算 | 只展示“待配置/未验证”，不推算券费用 |
| 财经云数据不完整 | 不得作为正式结算平台 | 保留准入入口，补齐后重新跑验证器 |
| SQLite 仍为本地 MVP 库 | 不适合多人业务使用 | 产品开发先以真实快照演示，生产使用前迁 MySQL 与服务层 |
| KPI 和分销基础数据未齐 | 不能承诺实际考核与分销结果 | 当前只提供规划入口和数据缺口说明 |

## 14 本 PRD 的决策

EC101 费用核销产品 V1 以“TPM 费用运营台”为定位，先实现对已有核算结果的可视、可追溯、可确认和可对账，不重建 DMS，不在页面复制核算规则。KPI 考核与分销管理从本期开始纳入信息架构与数据契约，但延后到基础数据齐备后开发。
